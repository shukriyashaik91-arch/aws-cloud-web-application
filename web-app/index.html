Project Overview

What This Project Demonstrates

A hands-on cloud architecture project that integrates eight core AWS services into a working, monitored, and cost-controlled web application.

🌐

Network Isolation

A custom VPC (10.0.0.0/16) with a public subnet, Internet Gateway, and route table separates the application from other AWS resources and gives full control over network configuration.

⚙️

Compute & Web Hosting

A single t3.micro EC2 instance running Ubuntu Server with Nginx hosts this portal. The web server logs every access request for later analysis.

🪣

Object Storage

A private Amazon S3 bucket stores website assets, archived access logs, and sample datasets. Access is controlled exclusively via an IAM Instance Role — no hardcoded credentials.

🔐

Identity & Access Management

IAM users, groups, and a least-privilege EC2 role ensure that every component has only the permissions it needs. SSH access is restricted to a specific IP address.

📊

Monitoring & Alerting

Two required project alarms are configured: CPU utilization and StatusCheckFailed. Alarms trigger SNS email notifications so issues are detected automatically without manual log inspection.

💾

Backup & Recovery

EBS snapshots capture the root volume state, providing a recovery point that can be used to restore or create a replacement instance after data loss or corruption.

Identity & Access Management

Manages users, groups, and roles. The EC2 instance uses an IAM role for S3 access — no static credentials are stored anywhere.

  • Least-privilege bucket policy
  • No access keys on EC2

Amazon CloudWatch
Monitoring & Observability

Collects EC2 metrics and triggers alarms when CPU exceeds 70 % or when status checks fail, enabling proactive issue response.

  • Two required project alarms configured
  • Integrates with SNS
📧

Simple Notification Service

Routes CloudWatch alarm notifications to email via the InternshipAWS-Alerts topic, alerting when the application requires attention.

  • Topic: InternshipAWS-Alerts
  • Email subscription confirmed
  • Triggered by CloudWatch alarms

Provides persistent block storage for the EC2 root volume. EBS snapshots provide point-in-time recovery using AWS-managed snapshot storage, separate from the project's S3 bucket.

  • 8 GB gp3 root volume
  • Snapshot for backup/restore
  • Snapshot storage is AWS-managed

Cloud Security

Security Principles Applied

Every component follows the principle of least privilege. No credentials are stored inside the application.

🏛️

IAM Roles (Not Keys)

The EC2 instance authenticates to AWS services exclusively through an attached IAM Instance Role. No access key ID or secret access key is stored on the instance or in any file.

  • Role: InternshipEC2S3Role
  • Credentials rotated automatically by AWS
  • No static credentials anywhere
⚖️

Least Privilege

The EC2 IAM role policy grants only s3:GetObject, s3:PutObject, and s3:ListBucket — and only against the specific project bucket ARN, not all S3 resources.

  • Bucket-scoped policy (not s3:*)
  • No EC2, IAM, or other service permissions
  • IAM users in groups with minimal rights
🛡️

SSH Access Restriction

The Security Group allows TCP port 22 only from a specific administrator IP address. SSH is never open to 0.0.0.0/0 (the entire internet).

  • Port 22 → Your IP only
  • Port 80 → Public (HTTP for demo)
  • All other ports blocked
🔒

Private S3 Bucket

The S3 bucket has Block All Public Access enabled. No bucket policy or ACL grants public read access. Objects are accessible only through authenticated AWS API calls using the EC2 role.

  • Block all public access: ON
  • No public bucket policy
  • No public ACLs
🚫

No Root Credentials

AWS root account credentials are never used for development. A separate IAM user (aws-project-user) handles normal administration tasks with only required permissions.

  • Root MFA is enabled
  • aws-project-user IAM user for daily work
  • Access keys not committed to git
📝

No Secrets in Code

The .gitignore file blocks .pem, .env, credentials, and key files from being committed. All sensitive values are passed at runtime through IAM, not stored in source code.

  • .pem files blocked by .gitignore
  • .env files blocked
  • No AWS access keys or secret credentials are hardcoded in the application

Backup & Recovery

EBS Snapshot Backup Strategy

EBS snapshots capture the complete disk state of the EC2 instance, stored durably in Amazon S3 (managed by AWS). A snapshot enables full volume recovery after data loss.

1

Identify the EBS Volume

Find the root volume ID attached to the EC2 instance in the AWS Console → EC2 → Instances → Storage tab. It will look like vol-0abc123def456.

2

Create an EBS Snapshot

EC2 → Volumes → Select volume → Actions → Create Snapshot. Add description InternshipRootSnapshot and tag it Project=InternshipAWS.

3

Snapshot Completes

AWS copies changed blocks to S3 (managed storage, not your bucket). Status changes from Pending to Completed. An 8 GB snapshot typically takes 2–5 minutes.

4

Restore: Create Volume from Snapshot

EC2 → Snapshots → Select snapshot → Actions → Create Volume from Snapshot. Choose the same Availability Zone as the original instance.

5

Documented Restore Procedure

If recovery is required, create a new EBS volume from the completed snapshot and attach it to an EC2 instance in the appropriate Availability Zone. The restored volume can then be mounted and used to recover the required data. Note: The restore procedure is documented as part of this project; a live restoration test was not performed.

6

Cost Note — Delete After Demo

EBS snapshots incur storage charges (not covered by Free Tier). Delete the snapshot after your internship demonstration to avoid ongoing costs. Always verify current pricing in the AWS Billing and Cost Management console.

Cost Control

Cost Control & Budget Management

This project is designed to use AWS resources economically and minimise unnecessary costs. Always verify current pricing and Free Tier availability in the AWS Billing and Cost Management console.

🆓

Free Tier Strategy

This project uses the smallest suitable instance type and minimal storage. Only the required project files and logs are stored in S3, and only the monitoring alarms required for the project are configured.

  • EC2: smallest suitable instance for the demonstration
  • EBS: minimal root volume size
  • S3: required project files and logs only
  • CloudWatch: only required monitoring alarms
  • SNS: email notifications for important alerts only
🚫

Expensive Services Avoided

The architecture intentionally avoids services that are not required for this demonstration and may introduce additional costs.

  • NAT Gateway
  • Application Load Balancer
  • RDS databases
  • Multiple EC2 instances
  • EKS / ECS clusters
  • Other unnecessary always-on resources
💰

AWS Budget Monitoring

AWS Budgets can be configured to notify the project administrator when spending reaches selected thresholds. Budget alerts help monitor spending but do not automatically prevent AWS charges.

  • Alert 1: $1.00 — monthly cost monitoring
  • Alert 2: $3.00 — monthly cost monitoring
  • Email notifications enabled
🧹

Post-Demo Cleanup

After completing the demonstration, remove resources that are no longer required to avoid unnecessary charges.

  • 1. Delete EBS snapshots no longer needed
  • 2. Terminate the EC2 instance
  • 3. Empty and delete the S3 bucket
  • 4. Delete CloudWatch alarms
  • 5. Delete the SNS topic
  • 6. Delete unused VPC resources
  • 7. Review Billing console for remaining resources

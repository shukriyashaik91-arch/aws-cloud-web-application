## Errors Found and Fixed

### ERROR 1 — `analyze_logs.py`: Wrong minimum Python version in docstring

**Severity:** Medium — would confuse anyone running the script on Python 3.8  
**Location:** `scripts/analyze_logs.py`, module docstring  
**Root cause:** The script uses PEP 585 built-in generic type hints
(`list[dict]`, `tuple[int, int]`, `dict[int, int]`) which require Python 3.9+.
The docstring stated `Requirements: Python 3.8+` which was incorrect.  
**Fix applied:** Updated docstring to `Python 3.9+` with an explanatory note.  
Also removed unused `import os` (style issue, no functional impact).  
**Verification:** Script runs correctly on Python 3.13 (local) and is
compatible with Python 3.10 (Ubuntu 22.04 on EC2).  

```
Before: Requirements: Python 3.8+  (no external libraries needed — stdlib only)
After:  Requirements: Python 3.9+  (no external libraries needed — stdlib only)
        Note: Python 3.9+ is required because the code uses PEP 585 built-in
              generic types (list[dict], tuple[X, Y], dict[X, Y]).
              Ubuntu 22.04 LTS ships Python 3.10 — fully compatible.
```

### ERROR 2 — `infrastructure/README.md`: Missing `CAPABILITY_NAMED_IAM`

**Severity:** High — the AWS CLI stack creation command would immediately fail  
**Location:** `infrastructure/README.md`, Deployment Order section  
**Root cause:** The CloudFormation template creates IAM resources with custom
names (`InternshipAWS-EC2S3Role`, `InternshipAWS-InstanceProfile`). AWS requires
the `--capabilities CAPABILITY_NAMED_IAM` flag to be explicitly passed on the CLI,
otherwise the create-stack call fails with:
`InsufficientCapabilities: Requires capabilities : [CAPABILITY_NAMED_IAM]`  
**Fix applied:** Added a clearly marked note with the exact CLI flag and explanation
of when it is required (CLI vs. Console checkbox).

## Fixes Applied to Deployment Docs

### FIX 3 — `infrastructure/deploy.md`: SCP target directory missing

**Severity:** Medium — SCP would fail silently or with a confusing error  
**Location:** `infrastructure/deploy.md`, Step 5  
**Root cause:** The original SCP command copied files to `/tmp/webapp/` but that
directory does not exist on a fresh Ubuntu instance. SCP to a non-existent
directory path fails with `No such file or directory`.  
**Fix applied:** Added `ssh ... "mkdir -p /tmp/webapp"` before the SCP command.
Also added clear instructions to copy the full project directory so that
`setup-server.sh` can locate files via `BASH_SOURCE`.  

**Before:**
```bash
scp -i ~/path/to/internship-keypair.pem \
    web-app/* \
    ubuntu@EC2-PUBLIC-IP:/tmp/webapp/
```

**After:**
```bash
ssh -i ~/path/to/internship-keypair.pem ubuntu@EC2-PUBLIC-IP "mkdir -p /tmp/webapp"
scp -i ~/path/to/internship-keypair.pem \
    web-app/* \
    ubuntu@EC2-PUBLIC-IP:/tmp/webapp/
```

### FIX 6 — `scripts/setup-server.sh`: BASH_SOURCE guard added

**Severity:** Medium — script silently fails to locate project files when run
via SSH stdin pipe  
**Root cause:** When a script is invoked as `ssh host 'bash -s' < script.sh`,
Bash sets `BASH_SOURCE[0]` to an empty string or `-`, making `dirname` return
`.` or an empty path. The `PROJECT_ROOT` variable would resolve to the wrong
location, causing the web-app copy and dataset upload steps to silently skip.  
**Fix applied:** Added a guard block at the top of the script that:
1. Detects the stdin-pipe execution mode
2. Emits a clear warning with correct usage instructions
3. Falls back to `/home/ubuntu/project` as a safe default path
4. Removes the duplicate `SCRIPT_DIR`/`PROJECT_ROOT` lines from Step 4
